# Runbook · 事件响应（P1）

> **适用场景**：平台 P1 事件 —— 监控丢失、Odoo 不可用、VPN 中断、服务器故障，或疑似网络安全事件。
> **方法依据**：NIST SP 800-61 事件响应生命周期
> **SLA 承诺**：收到告警后 **30 分钟内确认**，**1 小时内启动远程恢复**

---

## 事件分级

| 级别 | 定义 | 响应要求 |
|---|---|---|
| **P1** | 监控平台 / Odoo / VPN / 服务器丢失；疑似入侵 | 30 分钟确认，1 小时启动恢复，7×24 待命 |
| **P2** | 部分功能受损、单站点失联、性能劣化 | 当日工作时间内处理 |
| **P3** | 低优先问题、优化项 | 下个工作日 |

---

## 六阶段处置流程（NIST SP 800-61）

### 1. 准备（Preparation）—— 事件发生前

- [ ] Runbook 齐全且经过演练（本目录）
- [ ] 备份任务正常运行（`backups/backup.log`）
- [ ] 告警通道畅通（watchdog webhook 已配置）
- [ ] 待命人员与升级链明确

### 2. 检测与分析（Detection & Analysis）

收到告警后 **30 分钟内**完成：

```bash
# 服务状态总览
docker compose ps

# 编排层日志
docker compose logs --tail=100

# 看门狗告警记录
docker logs mog-watchdog --tail=30
```

判断关键问题：
- 是可用性问题还是安全事件？
- 影响面：全部站点还是单站点？
- 是否有近期变更（部署、配置、补丁）？

**记录时间线**（后续 RCA 用）：

| 时间 | 事件 |
|---|---|
| HH:MM | 收到告警 |
| HH:MM | 完成确认 |

### 3. 遏制（Containment）

**可用性事件**：优先恢复服务，缩短停机。
```bash
docker compose restart <service>     # 单服务重启
# 或依赖 watchdog 自愈
```

**安全事件**：优先阻断扩散，宁可短暂停机。

| 动作 | 命令/方式 |
|---|---|
| 隔离受损主机 | 从网络移除 / 防火墙封锁 |
| 轮换凭证与密钥 | 重置密码、重签 VPN 密钥 |
| 切断可疑连接 | 封锁对端 IP |

> 依据授权（Delegation of Authority）执行主机隔离、密钥轮换与恢复动作。

### 4. 根除（Eradication）

- 清除恶意软件 / 修复被利用的漏洞
- 撤销未授权访问
- 打补丁（关键补丁目标：发布后 14 天内）

### 5. 恢复（Recovery）

- 按 [data-restore.md](data-restore.md) / [server-rebuild.md](server-rebuild.md) / [vpn-recovery.md](vpn-recovery.md) 恢复服务
- 分阶段恢复，先核心（采集 + 数据库 + 看板）
- 密切监控恢复后状态（至少 24 小时）

### 6. 事后总结（Post-Incident Activity）

**5 天内**输出 RCA：

```markdown
## RCA · <事件标题>
- 事件时间：YYYY-MM-DD HH:MM ~ HH:MM
- 影响范围：哪些站点/服务/时长
- 根因（5 Whys）：
  1. 为什么...
  2. ...
- 修复措施：
- 预防措施（Runbook / 监控 / 架构 改进）：
- RTO 实际值：__ 分钟（目标 ≤ 60）
- RPO 实际值：__ （目标 ≤ 备份间隔）
```

## P1 待命检查表（on-call）

待命期间保持：
- [ ] 手机/通知可达，30 分钟内响应
- [ ] 可远程访问 ROC 环境
- [ ] 掌握当前未关闭的告警状态
- [ ] 明白休假时的 backup 顺序（ROC Lead + 外部 IT 支持）

---

## 安全事件特别提示（IEC 62443）

处置安全事件时践行"分区+导管"原则：
- 遏制动作在**导管边界**（防火墙/网关）执行，而非盲目拔线
- 优先隔离受损**分区**，保护其余分区的运行
- 记录所有跨区流量的异常，作为后续审计依据
